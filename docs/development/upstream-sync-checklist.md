# New API 上游同步注意事项检查单

本检查单用于 `origin/main` → 个人维护代码的日常同步。它只描述源码同步与开发环境验证，不授权生产发布；生产切换仍需单独备份、审批和验收。

## 0. 范围和安全边界

- [ ] 确认本次目标是同步官方源码，还是同时要构建测试镜像、切换测试环境或发布生产；未明确授权的动作不顺带执行。
- [ ] 确认生产控制目录、生产 Compose、生产数据库/Redis、生产 `data`/`logs` 路径不在本次源码合并的写入范围内。
- [ ] 不把 Token、密码、Cookie、私钥、真实连接串写入 Git、项目文档、交接包或命令输出。
- [ ] 生产环境禁止执行 `docker compose down -v`，禁止删除或重建生产数据库/Redis 数据卷。

## 1. 同步前基线

- [ ] 在实际开发 worktree 执行 `git status --short --untracked-files=all`、`git rev-parse HEAD`、`git branch --show-current`。
- [ ] 执行 `git worktree list --porcelain`，确认开发、生产源码和生产控制目录的职责没有混淆。
- [ ] 检查 `origin`（官方只读）和 `myfork`（个人 Fork）URL；确认目标分支和远端 SHA。
- [ ] 记录当前分支、HEAD、工作区状态、Compose/环境文件边界和未跟踪文件清单。
- [ ] 在同步前创建不可变回退点：`backup/pre-sync-<YYYYMMDD>`，并记录它指向的完整 SHA。
- [ ] 为需要长期保留的快照、测试日志和迁移证据创建 `.backups/new-api/<task-id>/`，不要覆盖旧备份。
- [ ] 检查未跟踪文件是否会与上游同名文件冲突；不确定时先备份并暂停，不擅自删除。

## 2. 刷新远端并审查范围

- [ ] 先 `git fetch origin --tags`，再按需 `git fetch myfork`；不使用强制覆盖本地分支的 fetch 参数。
- [ ] 记录官方目标 SHA、最近版本标签、基线与目标之间的提交数量：`git rev-list --count <base>..<target>`。
- [ ] 用 `git log --oneline`、`git diff --stat`、`git diff --name-status` 审查变更范围。
- [ ] 单独检查认证/会话、数据库迁移、计费/额度、Responses/Relay、渠道/模型、前端路由和依赖升级。
- [ ] 明确列出本项目私有改造（用量聚合 API、Web 统计页、Postman/文档等），逐项确认同步后仍应存在。

## 3. 分支与合并

- [ ] 从当前已验证的 `personal/main` 基线创建 `upgrade/upstream-main-<YYYYMMDD>`；不要在生产控制目录的 `main` 上开发。
- [ ] 已被多个 Agent/设备使用或已推送的 `personal/main` 使用普通 merge，不改写共享历史；仅对未共享分支使用 rebase。
- [ ] 使用 `git merge --no-ff --no-commit origin/main`，先查看冲突和统计，再决定如何解决。
- [ ] 官方安全、认证、迁移、计费和协议兼容逻辑优先保留；私有改造只在语义不冲突时保留，不能用整文件覆盖官方变更。
- [ ] 路由冲突要分别检查鉴权中间件、权限范围、审计记录和响应契约；新增私有路由必须仍受正确认证保护。
- [ ] 模型/日志/计费字段冲突要回到迁移代码和调用方核对语义，无法确定时停止合并并请用户决策。
- [ ] 前端冲突同时保留官方新增菜单/文案/路由和私有统计入口；生成文件优先使用项目生成命令重建。
- [ ] 合并后运行 `git diff --check`、`git status --short`，确认无未解决冲突、无意外删除或凭据进入暂存区。

## 4. 数据库与兼容性验证

- [ ] 列出官方新增/修改/删除的 migration、索引、约束、字段和数据回填；区分可逆与不可逆操作。
- [ ] 只在独立测试数据库副本上演练迁移，不把生产数据库直接用于开发测试。
- [ ] 记录旧库备份来源、SHA-256、关键表行数和旧镜像版本；切换新镜像后再次记录这些指标。
- [ ] 至少验证：首次启动迁移成功、第二次启动幂等、旧数据可读写、唯一性约束和关键索引有效。
- [ ] 对认证、计费、日志聚合、Responses/Codex、模型价格等私有/关键路径做接口回归。
- [ ] 报告中严格区分“测试副本验证通过”和“生产尚未验证”，不以容器 healthy 代替无损升级结论。

## 5. 构建与开发环境回归

- [ ] 只从开发 worktree 使用完整 Dockerfile 构建不可复用的开发镜像标签，并记录 commit、架构、镜像 ID/digest。
- [ ] 测试 Compose 使用独立项目名、端口、网络、PostgreSQL、Redis、`data` 和 `logs`，不挂载生产路径。
- [ ] 运行项目已有的 Go 测试、前端测试、类型检查、lint 和构建；记录实际命令与退出码。
- [ ] 冒烟检查 `/api/status`、登录/加密登录、`/v1/models`、`/v1/chat/completions`、`/v1/responses`、私有 usage-summary API 和 Web 统计页。
- [ ] 观察完整启动周期和后台同步日志，不只看第一秒的 healthy 状态。
- [ ] 失败时保留日志和镜像，不覆盖可回退版本；先定位根因再修复，不用连续重试掩盖问题。

## 6. 文档、提交与后续发布

- [ ] 在 `docs/development/release-log.md` 记录基线 SHA、目标 SHA、merge/rebase 方式、冲突处理、测试、迁移证据和未完成事项。
- [ ] 必要时创建交接包；主文件同时提供可点击的绝对路径和可复制的纯文本绝对路径，执行 Agent 回填反馈文件。
- [ ] 只暂存本次同步和文档相关文件，执行 `git diff --cached --check` 与 `git diff --cached --name-status`。
- [ ] 使用中文类型前缀提交，例如 `merge:`、`docs:`、`chore:`；本地 commit 不等于已获准 push 或生产发布。
- [ ] 完成源码和开发环境验证后，再单独请示是否快进/合并到 `personal/main`、推送 `myfork`、构建正式候选镜像或切换生产。
- [ ] 发布前重新执行生产备份、Compose 快照、镜像 digest 核验和回滚演练；未验证的同步分支不得进入正式 Compose。

## 推荐记录字段

每次同步至少保留：同步日期、开发分支、回退分支、基线/目标 SHA、官方版本、提交数量、冲突文件及处理理由、数据库副本和校验、测试镜像摘要、回归命令与结果、生产边界、下一步授权点。
